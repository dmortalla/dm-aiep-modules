# Module 6 User Guide

## Multi-Agent Systems & Orchestration — Reviewer Walkthrough

This guide provides a practical review path through the Module 6 Streamlit cockpit.

Module 6 demonstrates production-grade multi-agent orchestration with:

- LangGraph
- CrewAI
- Google ADK
- sequential, parallel, hierarchical, coordinator-worker, and distributed execution patterns
- application-owned workflow contracts and authority
- bounded cost and reliability controls
- real local Ollama inference for a trusted private operator
- LangSmith AI/agent tracing
- OpenTelemetry → Collector → Prometheus → Grafana operational observability
- explicit evidence classifications that separate deterministic, synthetic, real-local, recorded, and current evidence

The public reviewer deployment is intentionally deterministic and no-key. Public live execution is unavailable by design.

A focused first review takes about 15–20 minutes.

---

## 1. What You Need

### Public reviewer path

For the public deployed cockpit, you need only:

- a modern browser
- the deployed Streamlit URL

No provider key is required.

The public deployment supports:

- Guide
- Deterministic Demo
- recorded Operations evidence
- explicit current-host Operations checks
- recorded LangSmith evidence
- explicit current LangSmith inspection posture
- Implementation Evidence

The public deployment does **not** enable local Live/BYOK execution.

### Local deterministic review

For local zero-key use:

- Python 3.12
- this repository
- `uv`
- dependencies already available for offline synchronization

### Trusted-local Live/BYOK review

The real-local live path is for a trusted private operator only.

It requires:

- local execution through the private launcher
- Ollama available on the operator's machine
- the application-owned trusted runtime capability
- a fresh explicit authorization for each run

No secret is pasted into the Streamlit page.

---

## 2. Launch the Cockpit

From the repository root:

```powershell
uv sync --locked --offline
uv run --locked --offline python module-06/run_console.py
```

Open the loopback URL printed by the launcher, normally:

`http://127.0.0.1:8501`

The cockpit should open with six tabs:

1. **Guide**
2. **Deterministic Demo**
3. **Live / BYOK**
4. **Operations**
5. **LangSmith Tracing**
6. **Implementation Evidence**

The **Guide** tab is the recommended starting point.

Nothing executes, queries, or delivers merely because the page is rendered.

---

## 3. Understand the Evidence Classes

Module 6 deliberately separates evidence types.

### Deterministic demo

A real orchestration runtime executes with deterministic agents.

This can prove:

- scheduling
- graph structure
- validated hand-offs
- bounded execution
- local trace creation
- role ordering
- worker cleanup
- application-owned contracts

It does **not** prove model reasoning or live inference.

### Synthetic offline

The canonical workflow executes through a fixed synthetic gateway.

This can prove:

- the accepted workflow path
- validated role content
- accounting contracts
- bounded repair behavior
- local observation projection

It does **not** prove LLM inference.

### Local provider execution

A trusted-local workflow executes with real local inference through Ollama.

This is genuine real-local model execution.

It does not by itself prove:

- model quality
- hosted-provider support
- hosted deployment
- LangSmith delivery

### Recorded historical evidence

Preserved evidence from an accepted earlier run.

Recorded evidence is never presented as if it were a fresh current-host observation.

### Fresh execution

Evidence generated by an action taken in the current session or current host posture.

### `service_read`

A recorded LangSmith trace was programmatically read back from the service.

### `unverified_write`

A LangSmith delivery write received an accepted response, but no programmatic service read-back established that event.

These two delivery classifications must not be merged into a generic “delivered” claim.

# Walkthrough 2 — Run a Deterministic Multi-Agent Demonstration

## Goal

Execute a real orchestration runtime without model inference or external delivery.

## Steps

1. Open **Deterministic Demo**.
2. Choose a demonstration.
3. Leave the synthetic task text or replace it with non-sensitive sample text.
4. Start with:
   - **Step budget:** `8`
   - **Deadline:** `30000` ms
5. Press **Run demonstration**.
6. Inspect:
   - outcome;
   - workflow ID;
   - task ID;
   - application-validated evidence;
   - local trace;
   - root span;
   - validated role order;
   - worker PID evidence where applicable;
   - model-call and external-call counts.

## Expected result

A successful run should produce a validated local result with:

- evidence class `deterministic_demo`
- source `fresh_execution`
- zero model calls
- zero external calls
- local trace/span evidence

The exact role structure depends on the selected demonstration.

## What this demonstrates

This proves real runtime scheduling and application validation without relying on live model inference.

It does not prove:

- model reasoning;
- hosted execution;
- remote telemetry delivery;
- production capacity.

# Walkthrough 7 — Exercise Failure Controls

## Goal

Verify that invalid or over-budget work fails closed.

## Steps

1. Open **Deterministic Demo**.
2. Expand **Execution bounds and failure demonstrations**.
3. Try:
   - a graph with a step budget of `1`;
   - a very short deadline;
   - out-of-range control values.
4. Observe the resulting denial or timeout behavior.

## Expected result

The application should:

- reject invalid input rather than silently clamp it;
- report bounded failure;
- avoid automatic retry;
- avoid automatic fallback;
- preserve earlier valid results without presenting them as the result of the failed submission.

## What this demonstrates

Execution authority and safety policy remain application-owned.

The system does not reinterpret invalid input into a supposedly successful run.

# Security and Trust Boundaries

A reviewer should be able to verify all of the following:

- model output is untrusted data;
- user text is untrusted data;
- provider output is untrusted data;
- orchestration frameworks do not grant themselves application authority;
- execution policy, budgets, evidence, and telemetry semantics are application-owned;
- the deterministic public path is keyless;
- public live is unavailable by design;
- trusted-local live requires a separately injected capability;
- local live requires explicit operator action;
- each live run requires a fresh single-use authorization;
- no approval is remembered;
- rerenders never execute;
- no automatic retries occur in the accepted live profile;
- public deployment cannot execute the operator's local live path;
- credentials, where required by a provider, stay with the trusted runtime and are never entered into the public page;
- credential presence never grants execution authority;
- no automatic LangSmith write occurs from page rendering;
- no automatic Operations query occurs from page rendering;
- untrusted workflow/model/user/tool/provider data does not flow into the one static `unsafe_allow_html` CSS block;
- the cockpit exposes no iframe/component surface for Grafana, Prometheus, or LangSmith.

These controls establish tested authority and trust boundaries.

They do not establish universal prompt-injection immunity, public multi-user authentication, or general production security certification.

# Cost and Reliability Controls

The accepted NORMAL live profile uses:

- workflow budget: `200000 ms`
- per-call budget: `45000 ms`
- maximum model calls: `4`
- maximum repair attempts: `1`
- transport retries: `0`
- concurrency: `1`

Additional reliability controls include:

- explicit deadlines
- cancellation
- supervised child processes
- kill/reap behavior
- fail-closed denial
- no automatic fallback
- no automatic retry

The deterministic demonstrations also allow reviewers to exercise step-budget and deadline failures directly.

# Common Problems

## Live / BYOK is unavailable

That is expected in the public deployment and stock launcher.

Use the trusted private launcher only if you intentionally want real-local execution.

## Opening Live / BYOK does not probe Ollama

Correct.

The tab does not perform readiness probing just because it renders.

## The public deployment cannot see my local Prometheus/Grafana

Correct.

`localhost` means the machine hosting the Streamlit application.

A public deployment cannot inspect services on your personal workstation.

## The Operations check says unavailable

That is an honest fresh current-host result.

It does not invalidate the recorded local pipeline verification.

## LangSmith current check says unavailable

Expected in the stock/public posture.

No trusted read capability is supplied, so no read is attempted.

## A recorded LangSmith write says `unverified_write`

That is intentional.

A successful write response is not equivalent to a service-read confirmation.

## A first synthetic canonical run reaches the deadline

The application notes that local child-process warm-up can affect a first run.

Retry manually if appropriate.

No automatic retry occurs.

## A deterministic run reports zero model calls

Expected.

The deterministic reviewer paths use real orchestration runtimes with deterministic agents and no model inference.

## The benchmark shows speedup

Treat it as machine-specific local evidence only.

Speedup is not the pass criterion and should not be generalized into a production-capacity claim.

# What to Look For

A successful review should make these properties visible:

- multiple orchestration frameworks share application-owned contracts;
- deterministic runs use real runtime scheduling without model inference;
- role hand-offs are validated;
- parallel work synchronizes before aggregation;
- distributed execution produces genuine independent worker PIDs and cleanup evidence;
- budgets and deadlines are enforced;
- failures do not trigger silent retry/fallback;
- recorded evidence is never substituted for a failed current action;
- synthetic workflow evidence is never described as model reasoning;
- live local inference requires trusted runtime capability plus fresh authorization;
- public live is unavailable by design;
- historical and current observability evidence remain separate;
- LangSmith `service_read` and `unverified_write` remain separate;
- local Prometheus/Grafana verification is not represented as hosted production telemetry;
- implementation excerpts are not treated as proof of current runtime state;
- public deployment remains useful without credentials.
